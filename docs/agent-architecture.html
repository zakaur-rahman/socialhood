Social Hood Agent Architecture

How Social Hood's AI becomes a tool-using agent that understands a request, plans, calls typed tools, executes under deterministic policy, verifies the result and reports it. R1 ships a read-only agent; autonomy grows in R2 and R3 as evaluation, permissions and observability mature.

0Summary and decisions

The agent is an orchestration layer over the services Social Hood already has, not a second product. Sending, scheduling, automations, knowledge, analysis and the auto-reply policy keep their rules; the agent reaches them only through typed tools.

Decisions of record (owner, 2026-09-29)

  • R1 ships a read-only agent, "Ask Social Hood": read tools over conversations, comments, posts, analytics, knowledge and schedules. It may prepare an action card that the user completes in the normal UI. Write tools, approvals, permissions and the Copilot and Supervised modes are R2; Autonomous mode and standing conditional workflows are R3.
  • Framework: Pydantic AI, used only for the loop between the model and its tools. Run state, plans, approvals, permissions, credits and audit live in Social Hood's own Postgres tables; durability comes from the existing Procrastinate jobs.
  • Facebook Pages stays R2, LinkedIn posting R3; LinkedIn messaging is not possible (partner-only API).

Where this design differs from the brief, and why

  1. Tools are thin; services keep the rules. schedule_message calls the existing scheduling service, which already enforces the reply window, plan limits and idempotency. Nothing is written twice.
  2. One analysis call, not five modules. Sentiment, intent, topics, spam and lead score come from one model call per message (TR-AI-05) and one per comment batch (TR-AI-11). Splitting them would multiply cost by five.
  3. Plans are typed data; conditions are evaluated by code. The model writes a plan of steps and structured conditions; the executor runs it and decides whether a condition held.
  4. One action gateway for every write (R2): a tool's fixed risk tier, the requester's role, agent permissions, mode, bulk limits and platform capability decide execute, ask for approval, or refuse. The model's opinion is never an input.
  5. Verification is a read-back. Each write returns a receipt; a verifier reads the record back (and the platform, where it applies). Only then does the agent say it succeeded.
  6. Four tables, not eleven. agent_runs, agent_steps, agent_approvals, agent_policies. Memory reuses what exists: business memory is the knowledge base, customer memory is the contact plus conversation summary and analyses, task memory is the run.
  7. The agent lives beside ai/, not inside it. ai/ is model plumbing (providers, prompts, metering, policy). The agent orchestrates domain services, so it is its own package.

4Agent components

Planner (Pydantic AI)

A Pydantic AI agent with the workspace's tools registered and a dependency object carrying the database session, workspace, requesting member (the principal), time zone and run id. Two ways of working:

  • Answer loop (questions, R1): the model calls read tools, at most 8 tool calls and 6 model turns per run, then writes the answer. Every tool call is persisted as a step.
  • Plan first (anything with a write, R2): the model returns a typed Plan (steps, each a tool call or a condition), which is validated and shown to the member before any write runs. The executor then runs the plan itself; the model is called again only to re-plan after a failure (at most twice) and to write the final report.

Pydantic AI runs on Gemini through Social Hood's settings (AI_MODEL_AGENT, default the reply model). Every model call is wrapped in ai.metering.metered and recorded in ai_usage_events with feature agent_turn.

Plan and conditions

class Step:            id, tool, args (validated by the tool's schema), depends_on: [step ids],
                       when: Condition | None
class Condition:       left: Ref, op: ">" | ">=" | "<" | "<=" | "==" | "!=", right: Ref | number
class Ref:             step id + JSON path into that step's typed result, e.g. s2.engagement_rate

Conditions are evaluated by plan.evaluate() on stored tool results. A condition that refers to a missing value is false with a reason, and the report says which data was missing.

No separate vector memory. Remembering preferences ("always compare with 30 days") is an R3 idea and would be explicit, editable settings, not hidden embeddings.

Time resolver

agent/timeparse.py turns phrases into explicit values in the workspace time zone before tools run: instants ("tomorrow 7 PM" → 2026-09-30T19:00+05:30), ranges ("last week" → Monday–Sunday of the previous ISO week; "this month" → 1st to now; "the last 30 days" → now − 30 d to now) and ages ("after 24 hours"). The model passes the phrase; tools receive resolved values; the answer states them. Ambiguous input ("next Friday" on a Friday) is resolved by a documented rule and stated in the answer.

Action gateway (R2)

Every write tool is declared with a fixed risk tier and a capability. The gateway decides from those, the principal's role, the workspace's agent policy and the concrete arguments (for example, the number of recipients):

decide(tool, args, principal, policy) → EXECUTE | APPROVAL | REFUSE(reason)
  1. tool.release <= current release              else REFUSE not_available
  2. principal's role allows the action            else REFUSE forbidden
  3. policy.permissions[tool.capability] is on     else REFUSE agent_permission_off
  4. platform capability (TR-PL-11)                else REFUSE capability_unavailable
  5. limits: bulk size, per-hour and per-day caps  else REFUSE limit_reached
  6. mode × tier → EXECUTE or APPROVAL (table in §8)

Verifier

Each write tool has a verifier that reads the effect back: a scheduled message exists with the returned id and time; an automation exists with the requested trigger and is in the requested status; a comment reply has a platform id. Platform-side confirmation comes from the existing receipts (send results, echoes, webhooks). An unverified write is reported as "not confirmed", never as success.

Fair comparison

  • Instagram returns only lifetime totals at the moment you ask. Social Hood records snapshots at fixed ages after publishing (FR-ANL-01, now MUST in R1), so "this post after 24 hours" is compared with "previous posts after 24 hours".
  • A post younger than the requested age is compared at its current age against the baseline at the same age (interpolated between snapshots when needed), and the answer says so.
  • Posts published before the account was connected have no early snapshots; they join baselines only at ages they have, and the answer states the baseline size. With fewer than 3 comparable posts the agent says there isn't enough history.
  • Engagement rate = (likes + comments + shares + saves) ÷ reach at the same age; reported only when reach exists.
  • Reels and feed posts are compared within their format by default.

8Permission model

Three layers, all enforced in code, in this order. A request can never do more than the person who asked could do by hand.

  1. Member role (existing): agents (the member role) can read the inbox and act on conversations; owners and admins also manage automations, knowledge, publishing and settings. The principal's role bounds every tool.
  2. Agent policy (per workspace, owners and admins edit): mode, per-capability switches, limits.
  3. Tool risk tier (fixed in code, raised by arguments: a reply to more than one comment is high; more than bulk_max is refused).
Tier \ ModeRead only R1Copilot R2Supervised R2Autonomous R3
readrunrunrunrun
draftrun (action card)runrunrun
low (single reply, schedule a message, pause)refuseapprovalrunrun
high (bulk, send now, schedule or publish a post, activate automation)refuseapprovalapprovalrun within caps
destructive (delete automation, cancel published content)refuseapprovalapprovalapproval

Capability switches (all off until an owner turns them on in R2): send replies, schedule messages, schedule posts, create automations, delete automations, bulk actions. A switched-off capability refuses regardless of mode. The model can't change any of this; policy tools don't exist.

9Execution lifecycle

queued ──► planning ──► running ──► succeeded
   │           │           │  │
   │           │           │  ├──► partial      (some steps failed or were refused; report says which)
   │           │           │  └──► failed       (nothing useful done; error shown)
   │           │           ▼
   │           │    awaiting_approval ──approve──► running
   │           │           │  └──reject──► running (step skipped) or cancelled
   │           │           └──24 h──► expired
   └──cancel (member)──► cancelled
  1. Accept. POST …/agent/runs stores the run (queued), reserves nothing yet, enqueues run_agent, returns 202 with the run id. The panel subscribes to agent.* events.
  2. Understand and plan. The time resolver and context build the prompt; the planner either answers with read tools (R1) or returns a Plan (R2), which is validated: every tool exists and is allowed, arguments validate, dependencies form a chain without cycles, at most 12 steps.
  3. Execute. Steps run in order. Each is persisted before and after; writes pass the gateway; approval pauses the run and returns the job. Retries follow §15.
  4. Verify. Every write step runs its verifier; unverified becomes partial.
  5. Report. The model writes the answer from stored step results (no new facts: the report prompt receives only results), with citations. Status becomes final; agent.completed is published.

12Frontend plan

  • Ask Social Hood panel R1: opened from the top bar or /-style shortcut on any page, 420 px side sheet on desktop, full screen on phones; a full page at /w/[slug]/ask with thread history. Suggested prompts based on what exists ("How did my latest post do?", "What are people complaining about this week?").
  • Live steps: while running, a compact list of what the agent is doing ("Looking up your latest post", "Comparing with 10 earlier posts at 24 hours"), from agent.step events. No chain-of-thought is shown; only tool names in plain words and their outcomes.
  • Answer cards: numbers render as small tables and bar rows, with the time range, sample size and links to the posts, conversations or comments used. "Not enough data" and "insights not granted" are explicit states.
  • Action cards R1: "Schedule this message", "Open the automation draft", "Reply to this comment" open the existing screen pre-filled.
  • Plan preview and approvals R2: the plan as numbered steps with conditions; approval cards (what, to whom, how many, scope) with Approve, Edit, Cancel; an Approvals list in the panel and a notification.
  • Settings → Agent R2: mode, capability switches, limits, and a link to run history.
  • Run history R1: for admins, each run's request, steps, tools, results, credits and verification.

Conditional multi-step R2

"Analyse my latest Instagram post. If engagement is above my 30-day average and sentiment is
 positive, schedule a similar post tomorrow at 7 PM."

Plan (shown before running):
 s1 get_latest_post(instagram)
 s2 post_performance(s1.id, at_age = s1.age capped at 24h)
 s3 compare_posts(s1.id, baseline = posts in last 30 days, at_age = same)
 s4 sentiment_distribution(s1.id)
 s5 condition: s3.engagement_rate.delta_pct > 0  AND  s4.positive_share >= 0.6
 s6 draft_post_like(s1.id)            when s5   (caption draft, same media type; R3: generated)

                                        when s5   → gateway: high → approval card

Report: which conditions held (with numbers), what was scheduled, or why nothing was.

15Failure and retry

FailureHandling
Model timeout or 5xxRetry the model call once (the provider's retryable errors); then the run fails with "The AI didn't respond" and credits for failed calls are refunded (TR-AI-09)
Invalid tool arguments or planReturned to the model as a validation error once; a second invalid plan fails the run
Read tool errorRetried once if transient; otherwise the step fails and the model may continue with what it has; the answer says which data was unavailable
Write tool, transient platform errorRetried with the same idempotency key (existing send and schedule paths are idempotent); max 3 attempts with backoff
Write tool, permanent errorStep failed; dependent steps skipped; run ends partial with the platform's reason (e.g. "Instagram: outside the reply window")
Worker crash mid-runSteps are persisted before and after; the sweeper resumes from the last completed step; a write step that was running is re-checked with its verifier before any retry, so it never runs twice
Approval not given in 24 hExpired; the run ends partial and says what didn't happen
Credits run out mid-runNo new model calls; the run reports what it finished
Loop or runaway planHard caps: 12 steps, 8 read calls per answer, 6 model turns, 2 re-plans, 2 minutes wall time for R1 runs

16Observability and audit

  • Stored per run: request, principal, mode, plan, every step (tool, validated args, result summary, gateway decision, verification, external ids such as platform message or schedule ids, latency, attempts, errors), model and prompt version, tokens and credits, final answer and citations.
  • Not stored: the model's hidden reasoning. The trace is operational: what was called, with what, and what happened.
  • Logs: structured lines agent_step with run id, step, tool, status, latency; secrets and long text redacted as today (SEC-07).
  • Metrics and alerts: runs by status, p95 time to answer, tool error rate, refused writes, approvals pending and expired, credits per run. Alerts on tool error rate > 5% and on any write that failed verification.
  • Retention: runs and steps kept 180 days (the audit window), then summarised; deleting a workspace deletes them (§5.9 purge).

18Testing and evaluation

  • Unit: time resolver (a table of phrases × time zones × edge days), condition evaluation, plan validation, gateway decisions (every tier × mode × permission × role combination), verifiers, tool argument schemas.
  • Integration (FakeProvider scripting tool calls): each tool against real Postgres; tenancy (another workspace's ids never resolve); a run end to end with persisted steps; crash and resume; approvals (R2); caps.
  • Agent eval set (tests/ai_eval/agent.jsonl, ≥ 100 requests with expected tools, expected numbers from seeded data and forbidden behaviours): tool-choice accuracy, answer numbers matching the database exactly, no claims of actions not taken, correct refusals, time ranges resolved correctly. Run before any prompt or model change; results in docs/ai-eval-log.md.
  • Targets to ship R1: ≥ 90% correct tool choice, 100% numeric answers equal to the database, 0 invented numbers, p95 answer ≤ 12 s for single-tool questions.
  • Targets before each autonomy step (R2, R3): 0 unverified success claims and 0 writes outside policy over 2 weeks of shadow runs (the agent plans and the gateway decides, but nothing executes), reviewed by the owner.

20The final question

"Can Social Hood's autonomous agent safely operate the entire social-media workflow using tools, while analytics, permissions, platform APIs, business rules, and human approval remain under deterministic application control?"

Yes, for the workflows the connected platforms' APIs allow, and in stages. The architecture keeps every decision that matters out of the model:

  • Analytics: numbers come from typed queries over stored data and snapshots; the model only explains them.
  • Permissions: role, agent policy and tool risk tier are checked in code by the action gateway on every write; no tool can change the policy.
  • Platform APIs: reached only through the existing adapters, with their capability checks, rate limits, reply-window rules and idempotency.
  • Business rules: live in the existing services the tools call (scheduling, automations, sending, publishing, knowledge), so the agent inherits them.
  • Human approval: a persisted pause that only a person with the right role can resolve; edits are re-checked.
  • Truthfulness: success is claimed only after a verifier reads the result back; everything is traced per step.

"Entire workflow" has honest limits: no cold DMs, no Facebook until R2, no LinkedIn messaging, insights only with App Review. Within those limits the agent can analyse, decide and act, and autonomy is widened only after each stage's evaluation and shadow-run audit pass.
